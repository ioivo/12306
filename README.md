# 12306 铁路购票系统 — 高并发购票链路实践

> 面向海量并发抢票场景的微服务购票系统，重点解决「站点区间 × 座位类型」二维库存模型下的
> **超卖控制、缓存与数据库一致性、订单分库分表路由、查票性能**四类问题。
>
> 下文「核心改造」记录了在项目基础上完成的调整与实现。

## 二、核心改造

### 1. 余票扣减与超卖控制

**问题**：一辆列车途经 N 个车站，任意两站构成一个可售区间，同一座位在不同区间上的售卖互不冲突；
用户购买跨站车票时，需同时占用所有与之重叠的区间。若逐区间独立更新，中途失败会造成
「部分区间已锁、部分区间未锁」的不一致状态。

**方案**：
- 库存按「站点区间 × 座位类型」建模，`t_seat` 中一行代表一个座位在一个区间上的状态；
- 多区间扣减放在同一个数据库事务内完成，保证原子性；
- 按「车次 + 席别」加锁，不同席别的座位集合互不重叠，可并行出票；
- 锁座语句携带 `seat_status = 0` 条件并校验影响行数，以 CAS 方式避免覆盖已占用座位。

**效果**：并发压测下无超卖、无扣减错乱。

### 2. 缓存穿透防护

**问题**：注册查重时攻击者可构造大量不存在的用户名，缓存必然全部未命中，请求直接落到数据库。

**方案**：布隆过滤器前置拦截 + 数据库唯一索引兜底。
布隆过滤器无假阴性，判定「一定不存在」时直接放行、不访问数据库；仅在判定「可能存在」时回查一次。
最终一致性由 `t_user.username` 唯一索引保证。

**效果**：误判率配置为 0.001 时，数据库中约 0.1% 的查重请求会被穿透，其余均在缓存层拦截。

### 3. 缓存与数据库一致性

**方案**：Cache-Aside 模式。写路径只写数据库，通过 Canal 监听 binlog 并经 RocketMQ 异步
**删除**受影响的余票缓存 key，由下一次查询回源重建。

选择删除而非更新：删除天然幂等，且无需依据变更前状态推算增量，消息重复或乱序都不会算错。
代价是缓存失效后的首次查询需要回源聚合，该开销由 `idx_train_id` 索引承担。

**效果**：端到端不一致窗口为百毫秒级；窗口内不影响超卖判断，因为准入与扣减均不依赖缓存实时性。

### 4. 订单分库分表与查询路由

**问题**：订单需同时支持「按用户查我的订单」与「按订单号查订单详情」。订单表分片后，
若订单号与用户 ID 无关，按订单号查询将退化为 64 张物理表的广播。

**方案**：雪花 ID + 用户 ID 低 6 位构成订单号（基因法），使两个分片键经同一哈希后落在同一分片；
库与表分别由 `slot / 每库表数` 与 `slot` 推导，保证组合始终指向真实存在的物理表。

**效果**：两类核心查询均单分片路由，广播率为 0。

### 5. 查票接口性能优化

**问题**：v1 逐车次、逐席别读取票价与余票，一次查询产生数十次 Redis 网络往返，
响应时间被网络延迟主导。

**方案**：先收集全部 key，再用两次 `executePipelined` 批量读取票价与余票，把往返次数压缩到 2 次；
批量结果按车型对应的席别数量切分并组装。

**效果**：JMeter（100 线程 × 500 循环，5 万样本）下，吞吐由 1,589 提升至 3,445 QPS，
P95 由 69 ms 降至 19 ms。

> 上述压测数据在单机环境采集，压测工具与被测服务同机部署，仅用于版本间的相对对比，不代表生产容量。

### 6. 重复购票校验

**问题**：同一乘车人在同一车次上不应持有超过一张有效车票，否则会出现重复占座。

**方案**：在购票责任链中新增校验节点，按「车次 + 乘车人 + 有效状态」查询已出票记录；
待支付、已支付、已乘车视为有效，已退票、已关闭、已改签允许重新购买。
校验按乘车人维度而非下单账号维度进行，避免同一乘车人被不同账号代为购票时漏判。

**效果**：重复请求在进入选座与扣减环节前即被拦截，不占用锁资源。

## 三、系统架构

```
                    ┌──────────────┐
                    │   前端控制台   │
                    └──────┬───────┘
                           │
                    ┌──────▼───────┐
                    │ gateway 9000 │  JWT 校验 / 路由 / 限流
                    └──────┬───────┘
        ┌──────────────┬───┴───┬──────────────┐
        │              │       │              │
   ┌────▼────┐   ┌─────▼───┐ ┌─▼──────┐  ┌────▼────┐
   │  user   │   │ ticket  │ │ order  │  │   pay   │
   │  9001   │   │  9002   │ │ 9003   │  │  9004   │
   └────┬────┘   └─────┬───┘ └─┬──────┘  └────┬────┘
        │              │       │              │
        └──────────────┴───────┴──────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
   ┌────▼─────┐     ┌──────▼──────┐    ┌──────▼──────┐
   │  MySQL   │     │    Redis    │    │  RocketMQ   │
   │7库/268表  │     │余票/缓存/锁  │    │ 延时/异步    │
   └────┬─────┘     └─────────────┘    └─────────────┘
        │
   ┌────▼────┐
   │  Canal  │  binlog → MQ → 缓存失效
   └─────────┘
```

数据库划分为 7 个库、268 张物理表：用户库 2 × 32、订单库 2 × 32、支付库 2 × 32，
票务库为单库 9 张基础表（不参与分片）。

## 四、购票主链路

```
purchaseTicketsV2
├─ 责任链校验：参数、车次站点有效性、余票、重复购买
├─ 余票准入校验：一次 HGETALL 判断各席别余票是否充足（缓存未命中则放行）
├─ 加锁：按「车次 + 席别」升序获取 本地锁 → 分布式公平锁
├─ executePurchaseTickets（@Transactional）
│   ├─ 查询车次信息（缓存）
│   ├─ 选座：多席别并行，按区间过滤可用座位
│   ├─ 锁座：多区间多条 UPDATE，带 CAS 条件并校验影响行数
│   ├─ 写入 t_ticket（待支付）
│   └─ Feign 调用订单服务建单
└─ finally 逆序释放锁
```

## 五、本地运行

### 1. 启动中间件

```bash
docker compose up -d   # MySQL / Redis / RocketMQ / Nacos / Sentinel
```

数据库初始化脚本位于 `resources/db`（建表）与 `resources/data`（基础数据），需依次导入 7 个库。

> Redis 需支持 Bloom 模块（推荐 `redis/redis-stack-server`），否则注册查重会因缺少 `BF.ADD` 失败。

### 2. 启动微服务

按 `user → ticket → order → pay → gateway` 顺序启动，服务注册至 Nacos。
网关端口 `9000`，路由配置见 `gateway-service/src/main/resources/application-dev.yaml`。

### 3. 环境要求

- JDK 17
- Docker（建议 16 GB 内存以上）
- 中间件默认账号密码见各服务 `application.yaml`
